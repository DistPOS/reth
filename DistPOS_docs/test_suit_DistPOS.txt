
0) Общие условия и инструменты
    • Топология стенда: 4–7 узлов Reth-DistPOS (валидаторы A,B,C,D + наблюдатели), 2 независимые сети (Chain A / Chain B) с уникальными chain-id.
    • Фикстуры: genesis с адресами системных контрактов (Staking, BridgeToX/BridgeFromY), начальными стейками, корр.-счетами.
    • Артефакты/метрики: логи узлов, state root по блокам, снапшоты БД, RPC-метрики (prometheus), p2p-мониторинг.
    • Инструменты: интеграционный раннер (pytest/Go test/Rust cargo test), сценарные скрипты (bash/python), fault-injection (latency, drop, partition), метрики времени/успеха.

1) Локальный PoS: стейкинг, подписи, слэшинг
1.1 Регистрация валидатора
    • Предусловия: узел A без стейка.
    • Шаги: DistPOS_stake(A, amount) → проверка включения депозит-тx в блок.
    • Ожидание: A появляется в наборе валидаторов; A начинает предлагать блоки.
1.2 Производство блоков по очереди
    • Шаги: дать сети с A,B,C,D произвести N блоков.
    • Ожидание: блоки валидны, подписи соответствуют активным валидаторам, дрейф времени и высоты без остановок.
1.3 Отклонение блока без стейка
    • Шаги: убрать стейк у A (unstake), дождаться попытки A сгенерировать блок.
    • Ожидание: блок A отвергнут всеми, штраф не применяется (нет прав валидатора).
1.4 Слэшинг за двойную подпись
    • Шаги: сымитировать double-sign A на одном высотном уровне.
    • Ожидание: единый slashing-событие: уменьшение стейка A, отметка slashed=true, A исключён.
1.5 Crash/Restart устойчивость стейка
    • Шаги: во время применения слэшинга перезапустить A.
    • Ожидание: после рестарта состояние стейка консистентно (штраф применён единожды).

2) Андеррайтинг транзакций
2.1 Тx ≤ stake: без поручителей
    • Шаги: отправить tx от A со стоимостью ≤ stake(A).
    • Ожидание: tx попадает в блок без сборов поручительств.
2.2 Тx > stake: сбор поручителей
    • Шаги: отправить tx от A на сумму > stake(A); B,C отвечают UnderwriteResponse (общая сумма ≥ дефицита).
    • Ожидание: tx получает статус “подтверждена”, включена в блок; у B,C зафиксирован lockedStake.
2.3 Отказ в поручительстве → отклонение
    • Шаги: отключить ответы B,C; истекает таймаут.
    • Ожидание: tx снята из мемпула; A получает негативный результат; штраф по политике (если включено).
2.4 Отзыв поручительства
    • Шаги: B дал поручительство, но tx не включена; дождаться таймаута/UnderwriteCancel.
    • Ожидание: lockedStake(B) освобождён.
2.5 Плохая tx с поручителями
    • Шаги: собрать поручительства на заведомо невалидную tx, включить её.
    • Ожидание: отклонение при валидации/исполнении, штраф отправителю и (по политике) поручителям.
2.6 Устойчивость к спаму запросов
    • Шаги: A генерирует 100+ запросов андеррайтинга; B,C имеют ограниченный stake.
    • Ожидание: rate-limit, корректный отказ без деградации сети.

3) Межсетевой обмен (routing + Merkle)
3.1 Базовый cross-chain перевод A→B
    • Шаги: на A вызвать BridgeToB.lock(50); дождаться события; на B инициировать запрос proof; получить MerkleProofResponse; выполнить BridgeFromA.release.
    • Ожидание: у пользователя на B +50; на A списано 50; корр.-счёт A на B уменьшен на 50.
3.2 Недостаток авуара на корр.-счёте
    • Шаги: исчерпать корр.-баланс A на B; повторить перевод.
    • Ожидание: release ревертится в dry-run; узел B отклоняет включение.
3.3 Неверный proof
    • Шаги: подменить 1 байт в proof.
    • Ожидание: проверка Merkle отклоняет; перевод не включён.
3.4 Маршрутизация через альтернативный узел
    • Шаги: сделать недоступным узел B1; отправка идёт через B2 (из таблицы маршрутов).
    • Ожидание: доставка и подтверждение проходят.
3.5 Таймаут доказательства
    • Шаги: задержать MerkleProofResponse > TTL.
    • Ожидание: внешняя tx переводится в “expired”; средства на A можно отозвать (если предусмотрено).
3.6 Пакетная отправка
    • Шаги: 10–50 последовательных cross-тx.
    • Ожидание: очередь, корректная корреляция proof↔tx, отсутствие потерь.
3.7 Реорг в исходной цепи
    • Шаги: спровоцировать короткий реорг на A после эмиссии события lock.
    • Ожидание: B игнорирует proof не-финализированного блока; повторная проверка после финализации успешна.

4) Репутация узлов/цепей
4.1 Накапливание репутации за честную работу
    • Шаги: N блоков без нарушений.
    • Ожидание: рост score валидаторов по кривой.
4.2 Падение репутации за нарушения
    • Шаги: у A — спам андеррайтинга без покрытия; у C — попытка double-sign.
    • Ожидание: снижение score; пороговые эффекты (отказ в поручительстве, пониженный приоритет в мемпуле).
4.3 Репутация внешней цепи
    • Шаги: выставить низкий chain_rep(A); отправить cross-тx из A→B с валидным proof.
    • Ожидание: B отклоняет по политике доверия (лог: “низкая репутация источника”).
4.4 Восстановление репутации
    • Шаги: период честной работы после штрафов.
    • Ожидание: контролируемый рост score до порога.

5) Контракты (Staking/Bridge/CrossCall)
5.1 StakingContract: депозиты/слэшинг
    • Шаги: stake→slash→проверка storage.
    • Ожидание: корректные балансы/события; одинарное применение при форке/рестарте.
5.2 Bridge: lock/release happy path
    • Шаги: lock на A → release на B (с msg.data для целевого контракта).
    • Ожидание: атомарность: перевод + вызов target.call выполнены.
5.3 Bridge: отказ по условиям
    • Шаги: release с недостатком корр.-баланса/запрещённым msg.data.
    • Ожидание: revert; узел не включает tx.
5.4 Адреса системных контрактов
    • Шаги: валидация, что адреса из genesis; при апгрейде адрес изменён синхронно на всех узлах.
    • Ожидание: расхождений нет; блоки с “старым адресом” отвергаются.

6) Сетевые сбои и устойчивость
6.1 Network partition (A|B,C,D)
    • Шаги: разделить сеть на 2 компоненты; дать выпускать блоки 1–2 эпохи.
    • Ожидание: после восстановления — консенсус сходится, финализация без двойных финалов.
6.2 Потеря/дубликаты p2p-сообщений
    • Шаги: дропать 30% Underwrite* и Merkle* сообщений, вставлять дубликаты.
    • Ожидание: отсутствие зависаний; идемпотентность обработки.
6.3 Перезапуск узлов под нагрузкой
    • Шаги: рестарт B и C во время андеррайтинга/cross-chain.
    • Ожидание: корректное восстановление in-flight состояний (pending endorsements, pending proofs).

7) Производительность и масштабирование
7.1 TPS локальных транзакций
    • Метрика: пиковый TPS при 0% cross-chain, 0% underwriting; задержка подтверждения.
    • Ожидание: не хуже базового Reth-референса ±допустимое отклонение.
7.2 Underwriting overhead
    • Метрика: средняя задержка подтверждения для tx > stake при разном числе поручителей.
    • Ожидание: линейное/сублинейное увеличение задержки, без таймаутов при нормальной нагрузке.
7.3 Cross-chain throughput
    • Метрика: tx/sec межсетевых переводов при разных размерах proof и глубине очереди.
    • Ожидание: стабильная очередь, bounded latency.
7.4 Память/диск
    • Метрика: рост БД/ОЗУ на 10k endorsements и 5k pending proofs.
    • Ожидание: без утечек, GC штатно, БД рост предсказуем.

8) Безопасность и негативные кейсы
8.1 Replay/duplicate proof
    • Шаги: повторно применить уже израсходованный proof.
    • Ожидание: детект и отказ (idempotency).
8.2 Подмена chain-id / spoofing отправителя
    • Шаги: изменить метку chain-id при пересылке.
    • Ожидание: несоответствие домена → отказ.
8.3 Sybil поручителей
    • Шаги: один актор имитирует N узлов-поручителей с малым stake.
    • Ожидание: политика min-stake-per-endorser/репутация блокирует схему.
8.4 DoS на эндорсинг
    • Шаги: массовые UnderwriteRequest от злоузла.
    • Ожидание: rate-limit, штраф репутации, отсутствие деградации.
8.5 Неправильные системные транзакции
    • Шаги: “вручную” вставить блок с вызовом Bridge.release без proof/баланса.
    • Ожидание: узлы отвергают блок на валидации.

9) Восстановление и согласованность состояния
9.1 Crash mid-block
    • Шаги: аварийный стоп во время применения блока со слэшингом/release.
    • Ожидание: после рестарта — ровно один эффект (no double-apply).
9.2 Reorg-aware underwriting
    • Шаги: endorsements собраны, но лидерский блок ушёл в реорг.
    • Ожидание: корректная переоценка состояния; повторный сбор при необходимости.
9.3 Persistency pending queues
    • Шаги: рестарт с незавершёнными pending endorsements/proofs.
    • Ожидание: очереди восстановлены из БД/журнала; процесс продолжен.

10) CI/CD и критерии приёмки
    • Автоматизация: один командный раннер поднимает 2 сети, запускает сценарии, собирает метрики и артефакты; отчёт в JUnit + графики Prometheus.
    • Gate-условия релиза:
        ◦ Успех 99% happy-path тестов (1.x–3.x, 5.x).
        ◦ Нулевой rate расхождений стейта после crash/restart (9.x).
        ◦ Порог по perf: деградация TPS ≤ X%, p95 latency ≤ Y сек (7.x).
        ◦ Успешная обработка всех негативных кейсов без паник/утечек (8.x).
    • Рандомизация: ночные property-based тесты (разные seed’ы: размер стейка, количество узлов, задержки сети).
    • Регрессия: фиксация метрик между сборками; алерты на ухудшение.
